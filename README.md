# Automated Timetable Generation

A team coursework prototype using Python, Pandas, Excel and Flask to explore greedy course scheduling across 24 weekly teaching slots. This is an educational archive, not a production scheduling or student-record system.

He prepared data and technical documentation. The scheduling engine and interface are team project code, not his independent implementation claim.

## Privacy-safe local demo

The original student/faculty spreadsheets are not included. `make_example_data.py` creates three tiny, entirely synthetic workbooks with demo courses, generic faculty names and fake student IDs. The fourth workbook, `Master_Timetable.xlsx`, is generated by the app as output. None of these generated files should be committed.

```bash
python -m venv .venv
# Activate .venv.
pip install -r requirements.txt
python make_example_data.py
python app.py
```

Open the local URL printed by Flask. Try demo student `1001` or `1002`. ID `8` opens the coursework's master-table view. This is a demo switch, NOT authentication. Do not expose the server to the internet or use real student records.

Run the example generator from a clean checkout. It refuses to overwrite existing workbooks. The app writes `Master_Timetable.xlsx` on startup. Generated input and output files are ignored by Git.

## Algorithm limits

The implementation greedily places courses in faculty-available slots and caps each slot at two courses. It is not a complete constraint solver.

- The student conflict resolver can change a displayed course time without updating the master schedule or checking faculty availability again. A conflict-free-looking personal view is not proof of a valid schedule.
- It does not enforce every teacher, room, capacity or cross-student constraint.
- Slot order is randomized, so schedules can differ across runs.
- There is no authentication, authorization, durable database or production input-hardening layer.
- Shared state is initialized by the script entry point, not an application factory; run `python app.py` for the demo rather than assuming a WSGI deployment works.

These limits are documented rather than silently presenting new scheduling logic as the original team's work. Do not use the prototype for real course allocation.
